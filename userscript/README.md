# KhanWars Toolkit — سكربت Tampermonkey

سكربت متصفح يحوّل كل ما بنيناه في `analysis/` إلى أداة جاهزة تعمل تلقائياً داخل صفحات اللعبة، بدون Console وبدون تنقّل.

- الملف: `userscript/khanwars-toolkit.user.js`
- الإصدار: `1.5.9`
- العالم: أي عالم على `*.game.khanwars.ae` أو `*.game.khanwars.com`

---

## التثبيت

1. ثبّت إضافة **Tampermonkey** من متجر المتصفح (Chrome / Edge / Firefox).
2. افتح أيقونة Tampermonkey → **Create a new script** (أو Dashboard → `+`).
3. امسح المحتوى الافتراضي، والصق كامل محتوى `userscript/khanwars-toolkit.user.js`.
4. `Ctrl + S` للحفظ، ثم افتح/حدّث صفحة اللعبة.

بعد التحديث تظهر لوحة **KhanWars Toolkit** أسفل يسار الشاشة (أو زر صغير `KW` إذا كانت اللوحة مغلقة).

> بديل: Tampermonkey Dashboard → **Utilities** → Import from file، واختر الملف مباشرة.

## الاستخدام

### تبويب الإرساليات
- يُحدّث تلقائياً عند فتح اللوحة.
- زر `⟳` لإعادة القراءة.
- **تحديث تلقائي** (اختياري): 10ث / 20ث / 30ث / دقيقة / دقيقتين.
- الأعمدة:

| العمود | المعنى | المصدر |
|---|---|---|
| `#` | رقم الإرسالية | `data.timers` |
| النوع | هجوم / دعم / دورية … | `a[name^="marchTypes_"]` |
| المُرسِل | مالك قلعة المصدر | مالك رابط `marchesCastleFrom_` |
| المُستقبِل | مالك قلعة الوجهة | مالك رابط `marchesCastleTo_` |
| القلعة المستهدفة | اسم/وسم قلعة الوجهة | `marchesCastleTo_` |
| المسار | القلعة المصدر → القلعة الهدف | `marchesCastleFrom_/To_` |
| **الكلي** | **المدة الكلية** `HH:MM:SS` | `data.marchTimes[id]` (احتياطي: `info.php`) |
| المتبقي | عدّاد حيّ بالثانية + شريط تقدّم | `data.timers[id]` محلياً كل ثانية |
| العودة | وقت العودة `ستعود` | `info.php` |
| 👥 | عدد السكان (الرجال) | `info.php → li#population` |
| 📦 | الحمولة (مجموع السعة) | `info.php → li#cargo` |

- عند وصول العدّاد لصفر تظهر «انتهت»، ويُعاد التحديث تلقائياً مرة واحدة بعد ثانية ونصف.
- الإرساليات المعلّقة تظهر في سطر المعلومات أعلى الجدول.
- هجوم وارد إلى قلعة اللاعب يظهر بتنبيه أحمر ويُعلّم صفه. التصنيف يعتمد على مالك المصدر والوجهة ومقارنة الوجهة باسم اللاعب أو القلاع المعروفة؛ إذا تعذر تحديد الملكية لا يصنفه كتهديد مؤكد.
- بيانات الهجوم الوارد جاهزة لربط تنبيه لاحق عبر `KW.incomingAttacks()`، ولا يرسل السكربت رسائل تيليغرام حالياً.

### تبويب المباني
- زر **تحميل / تحديث** يجلب `buildings.php` ويحلل كل `.buildingItem`.
- يعرض: الاسم، المستوى الحالي، المستوى التالي، التكلفة (ذهب/حديد/خشب/طعام)، وقت البناء.
- زر **ترقية** يرسل `buildings.php?tb_id=<id>&method=ajax` بعد تأكيد.
  - هذا الإجراء **يغيّر حالة اللعبة** (يصرف موارد ويأخذ طابور البناء).
  - عند الفشل تظهر رسالة الخادم نفسها (مثل «الذهب غير كافي» أو «جدول مهام البناء ممتلئ»).

#### البناء الآلي (تنفيذ طابور جاهز)
- متوافق مع **KhanWars Build Queue Manager – Premium** (سكربت إضافة الطابور) دون تعديله:
  يقرأ `khanBuildQueues` بنفس صيغة مفاتيحه ويستهلك العنصر المنفَّذ فقط.
- اللوحة **تقرأ الطابور من `localStorage` وتنفّذه** — لا إضافة ولا حذف ولا ترتيب من الواجهة.
- شريط أخضر أعلى التبويب: **▶ تشغيل آلي** / **■ إيقاف**، وخيار **كل القلاع**.
- الطابور يظهر كشرائح مرقّمة **للقراءة فقط**:
  - الأخضر = مهمة/مكافأة (`101..135`) — تُستلم مكافآتها الجاهزة في مكانها.
  - الأحمر = مهارة/عنصر غير مدعوم (`>135`، مثل `150`) — يُتخطّى دون حذف.
  - المتوسط (مشطوب) = محجوب بشرط مسبق في هذه الجلسة (في الذاكرة فقط، بدون تعديل الطابور).
  - الأزرق = أُرسلت ترقيته وبانتظار **تأكيد المستوى**.
- المنفّذ يشتغل من **أي صفحة** — لا حاجة لفتح `buildings.php` ولا لإعادة تحميل الصفحة:
  - **تحقق 100% بمقارنة المستوى (وضع صارم):** لا يبدأ ترقية جديدة قبل أن يصبح جدول البناء **فاضياً تماماً** وتُتأكَّد الترقية السابقة:
    1. يقرأ مستوى المبنى قبل الإرسال من `ajax_buildings.php` (رد خفيف ~4KB) ويحفظه في `kw.pendingBuilds`.
    2. يرسل الترقية بنفس طلب اللعبة `buildings.php?tb_id=N&method=ajax`.
    3. **بعد ردّ النجاح** يقرأ المستوى فوراً (حتى 3 محاولات خلال ~3 ثوانٍ)، لأن اللعبة قد تُظهر **المستوى التالي** بمجرد قبول الترقية:
       - ارتفع فوراً ⇒ نجاح مؤكد ⇒ يحذف العنصر من الطابور مباشرة.
       - لم يظهر بعد ⇒ يبقى العنصر معلّقاً في `kw.pendingBuilds`، ويُعاد التحقق عند فراغ جدول البناء (سلوك النسخة السابقة).
    4. `المستوى بعد > قبل` ⇒ نجاح مؤكد ⇒ يحذف العنصر؛ ويبقى المستوى كما هو بعد قراءتين عند فراغ الجدول ⇒ فشل ⇒ **يبقي العنصر** ويعيد ترقيته تلقائياً.
  - يملأ طابور البناء حتى **عنصرين كحد أقصى**؛ يبقى التحقق من المستوى لتأكيد العناصر المرسلة وإزالتها بعد النجاح.
  - **الترقية المعلّقة تبقى محفوظة عند إعادة تحميل الصفحة** (`kw.pendingBuilds`) — لا تكرار ولا ضياع.
  - **ردّ شبكة غير واضح / لا رد** → لا يعيد فوراً؛ يعتبره «تحقق معلّق» ويسأل عن المستوى أولاً، حتى لا يبني نفس المبنى مرتين.
  - **مبنى بأعلى مستوى** («تم الوصول لاعلى مستوى!») → يُحذف من الطابور مباشرة (لا مستوى أعلى لينتظر).
  - **البناء مشغول** («جدول مهام البناء ممتلئ» أو «يتم بناء مبنى اخر حالياً») → يقرأ متبقي أول بناء وينام على أساسه (بدون انتظار ثابت).
  - **موارد غير كافية** («الذهب غير كافي») → ينتظر 120ث ويعيد.
  - **شرط مسبق** («يجب عمل بعض التطويرات اولاً») → يحجب العنصر في هذه الجلسة وينتقل للمبنى التالي؛ يُصفَّر الحجب بعد أي ترقية ناجحة، وإن حُجب كل المباني **يبقى شغالاً** ويعيد المحاولة تلقائياً كل 90ث. **لا يعيد ترتيب طابورك.**
  - **خطوات المهام/المكافآت (`101..135`)**: يستعلم أنواع المهام الأربعة (`Production/Military/Knights/Upgrades`)، ويستلم فقط المهام التي `data.isClaimable = true` عبر `ajax_quester_v63.php` (`Quest_UI_Base` + `claimReward` + `forceClaim:1`) ثم يحذف خطوة المهمة من الطابور. لا يستلم مهمة غير مكتملة إطلاقاً.
  - **لا يوجد مبنى إطلاقاً** (الطابور كله `>135`) → **لا يتوقّف**؛ ينتظر تعديل الطابور ويعيد الفحص كل دقيقتين.
  - **أي خطأ آخر** → **لا يتوقّف**؛ يعيد المحاولة بتباعد تصاعدي (60ث ← 120ث ← … بحد أقصى 5 دقائق).
  - **الطابور فاضي** → **لا يتوقّف أبداً**؛ يبقى شغالاً بانتظار عناصر جديدة (فحص محلي كل 15ث، بدون أي طلبات سيرفر). عند إضافة المدير/أنت عناصر جديدة يستأنف تلقائياً.
- **لا يتوقّف التشغيل الآلي إلا بأمرك** (زر ■ إيقاف / `KW.autoBuildStop()`) — كل الحالات أعلاه انتظار وإعادة محاولة، وليس إيقافاً.
- سطر الحالة يعرض الحالة + العدّاد للانتظار + اسم الترقية المنتظرة، وسجل قصير يعرض آخر العمليات.
- **كل القلاع**: عند فراغ طابور القلعة الحالية ينتقل تلقائياً (عبر `fetch` بدون تنقّل) لقلعة أخرى عندها طابور، ثم يكمل. وإذا كانت هناك ترقية معلّقة في قلعة أخرى يعود إليها أولاً للتحقق من مستواها قبل أي بناء جديد.

#### جدول البناء الحقيقي + الإنهاء الفوري المجاني
- قبل أي طلب بناء يقرأ المنفّذ جدول البناء الحقيقي بطلب واحد صغير:
  `POST ajax_bottomBar.php` → `{ type: 'load', bar_type: 1 }`
  يعيد `data.timers` (ثواني متبقية لكل عنصر) و`data.buildTimes` (المدة الكلية).
- **لا يزيد طابور البناء عن عنصرين** (`MAX_BUILD_QUEUE = 2`)؛ عند وجود خانة متاحة يمكن إرسال العنصر التالي دون انتظار انتهاء الأول.
- **التحقق لا يعتمد على معرّف المؤقّت:** مفاتيح `data.timers` هي **معرّفات عملية Build Process** (مثل `122900`) وليست معرّفات المباني. لذلك لا نحاول مطابقة المبنى بمعرّف المؤقّت، بل نعتبر **فراغ الجدول** علامة انتهاء الترقية، ثم نقارن المستوى.
- **لا نوم عشوائي**: يقرأ متبقي **أول** بناء وينام `متبقي - 60ث` بحد أقصى **5 دقائق**، ثم يقرأ الجدول مرة أخرى.
  - أثناء وجود ترقية معلّقة لا ينام أكثر من **60 ثانية**، حتى لو أنهاها اللاعب يدوياً أو فُتحت صفحة أخرى.
  - إن كان الجدول فاضياً يرسل الترقية فوراً بلا نوم.
  - إن كان فيه بناء (سواء واحد أو اثنان) ينام حتى يدخل آخر دقيقة أو 5 دقائق (أقربهما)، ثم يتحقق.
- **إنهاء فوري مجاني**: عندما يصبح متبقي أول بناء **60 ثانية أو أقل** — وهي الحالة التي تجعل اللعبة الإنهاء مجانياً — يرسل المنفّذ نفس مسار زر «السرعة» في اللعبة:
  `POST ajax_instantProcess.php` → `{ type: 'getPopupStatus', process_type: 1, instantFinishTimeReached: 'true' }`
  ثم يتحقق من `ajax_bottomBar.php` أن العنصر اختفى فعلاً (وإلا يجرّب `instantProcess` بالمعرّف كاحتياطي). بعدها يتحقق من ارتفاع المستوى ويحذف عنصر الطابور.
- خيار في الشريط: **⚡ إنهاء فوري ≤60ث** (مفعّل افتراضياً، يُحفظ في `kw.instantFinish`).
- كل الطلبات تُرسل بـ `evalJS: false` كي لا تُنفِّذ ردود السيرفر النصية (اللعبة تعيد أحياناً `window.location = ...`).

- **توافق مفاتيح الطابور (نفس صيغة مدير الطابور):**
  - `khanBuildQueues[revIdx]` — المصدر (يُقرأ، ويُستهلك فقط عند التنفيذ).
  - `revIdx = 11 - عدد القلاع + (رقم القلعة)`.
  - **اسم القلعة ومعرّفها** يُقرآن من `ajax_castles.php` (طلب Ajax صغير يعيد القائمة كاملة: الاسم، `#id`، الإحداثيات، والحالية).
  - تُحفظ القائمة في نفس متغيّري كود القلاع القديم (ويقرأهما مدير الطابور لبناء قائمته):
    - `castle_name` = أسماء القلاع بالترتيب، مثال: `["rambo"]`
    - `castle_id` = معرّفاتها بنفس الترتيب، مثال: `[342]`
  - إضافة إلى كاش داخلي `kw.castlesCache` يُحدَّث كل **5 دقائق** فقط، أو بعد تبديل القلعة → **أقل حمل ممكن**: لا طلب قلاع عند كل صفحة، ولا تنقّل بين صفحات.
  - سطر أعلى الطابور يوضّح: `القلعة: <الاسم> #<id> <الإحداثيات> • khanBuildQueues[<المفتاح>]`.
  - لا اعتماد على نصوص `castle_name` ولا على مطابقة الأسماء.
  - احتياطي: إذا لم يُطابق المفتاح المحسوب شيئاً وكان في `khanBuildQueues` **مفتاح واحد فقط غير فاضي**، يُستخدم هو (يغطّي حالات مثل تخزين المفتاح `NaN`).

### تبويب الحداد
- يقرأ فئات التطوير الخمس (`u_type=1,5,2,4,3`) بطلبات `fetch` خلفية، ويعرض مستوى الهجوم والدفاع لكل وحدة دون فتح صفحات الحداد. يقرأ عناصر التنفيذ من `localStorage['smithUpgradeQueue']` مباشرة.
- مع قلعة واحدة يختارها تلقائياً. عند تعدد القلاع تظهر قائمة **قلعة التطوير**، ويجب اختيار القلعة المقصودة (مثلاً العاصمة `ي-8-`) قبل القراءة أو التشغيل. اختيارها يبدّل القلعة في جلسة اللعبة بطلب خلفي، بلا انتقال للصفحة.
- المستويات محفوظة لكل قلعة في `kw.smithy.data.<castleId>`، مع تحديث `unitLevelsById` للتوافق مع الأدوات القديمة. الطابور يبقى بصيغة `smithUpgradeQueue`: `[unitId, 1]` للهجوم و`[unitId, 0]` للدفاع.
- الطابور **للقراءة والتنفيذ فقط** داخل الأداة. داشبوردك الحالية تظل مسؤولة عن الإضافة والحذف والترتيب؛ لا يكتب السكربت إلى `smithUpgradeQueue` ولا يضيف/يحذف/يعيد ترتيب عناصره.
- خيار **تطوير تلقائي** يرسل طلبات الحداد للقلعة المختارة فقط. الحد الصارم هو **أمران كحد أقصى**: قبل كل إرسال يعيد قراءة الخانات من `ajax_bottomBar.php` مع `bar_type=3`، ولا يرسل إذا كانت الخانتان مشغولتين. يستخدم فئة الوحدة المستخرجة من صفحة بياناتها.
- عند امتلاء الخانتين، يعرض الوقت المتبقي لأول تطوير ويحدّث العدّ التنازلي محلياً كل 5 ثوانٍ بلا طلب جديد. يعيد فحص الخادم قرب انتهاء المؤقّت، وبحد أقصى كل 10 دقائق إذا طال الانتظار، ثم يرسل العنصر التالي بعد تأكده من توفر خانة؛ إذا لم تتوفر مؤقّتات صالحة يرجع للفحص الدوري القصير.
- إذا تعذّر بناء عنصر بسبب نقص الموارد، يبقى في رأس الكيو ويحافظ السكربت على ترتيب العناصر؛ يقرأ تقدير اللعبة للوقت اللازم لتوفر الموارد ثم يعيد محاولة المبنى نفسه، مع دقيقتين كمهلة احتياطية إذا لم يتوفر تقدير.
- قبل أي طلب يغيّر حالة اللعبة (بناء، تطوير حداد، إرسال الأمير، استلام مكافأة أو مهارة)، يتحقق السكربت عبر `ajax_castles.php` أن القلعة النشطة تطابق القلعة المقصودة. قفل مشترك يمنع بدء تبديل القلعة حتى ينتهي التحقق والطلب؛ إذا كانت القلعة مختلفة يمنع الإرسال.
- لتجنب إعادة إرسال نفس العنصر بينما يبقى في طابور الداشبورد، يسجل السكربت حالة الإرسال منفصلة في `kw.smithy.sent.<castleId>`. بعد استجابة HTTP ناجحة يبقى عنصر الطابور مكانه، ويمكنك إزالته من داشبوردك عند الحاجة. راقب أول استجابة من اللعبة قبل الاعتماد على التشغيل التلقائي.
- وظائف Console: `KW.smithy.refresh(cb)`, `KW.smithy.queue()`, `KW.smithy.setCastle(id)`, `KW.smithy.setAuto(true|false)`, `KW.smithy.status()`.

الملف الرئيسي يتضمن الآن مزامنة مستويات الحداد وقراءة طابوره وتنفيذه. لا تثبّت سكربتات مزامنة/أتمتة الحداد المنفصلة بالتوازي معه؛ داشبوردك الحالية تبقى مستقلة ومسؤولة عن تعديل الطابور.

### تبويب JSON
- آخر رد كامل (إرساليات/مباني/قلاع) بصيغة JSON، مع زر **نسخ**.

### تبويب القلاع
- يعرض كل قلاع الحساب من `ajax_castles.php`: الاسم، الإحداثيات، السكان، الولاء، والقلعة **الحالية**.
- زر **تبديل** يغيّر القلعة النشطة في جلسة اللعبة عبر طلب سيرفر واحد فقط، **بدون مغادرة الصفحة أو إعادة تحميل**:
  - الطلب: `GET main.php?tpid=<id>&location=<الصفحة الحالية>`
  - بعد الطلب يتحقق السكربت من `ajax_castles.php` أن `class="current"` انتقل فعلاً للقلعة المطلوبة.
  - عند النجاح تُصفَّر بيانات المباني (لأنها خاصة بالقلعة) ويُعاد تحميلها إن كان تبويب المباني مفتوحاً.
- **دورة كاملة**: يزور كل قلعة مرة واحدة (3 ثوانٍ بين كل قلعة) ثم يعود للقلعة الأصلية.
- **تبديل تلقائي** + فاصل (5/10/20/30/60ث): ينتقل بين القلاع دورياً.
  - يتوقّف تلقائياً بعد 3 محاولات فاشلة متتالية.
- **مع قلعة واحدة** تُعطَّل كل أدوات الدوران والتبديل تلقائياً (لا يوجد ما يُدار)، وتظهر رسالة توضيحية.

> ⚠️ بعد التبديل تبقى واجهة اللعبة العلوية تعرض القلعة القديمة (لأن الصفحة لم تُحدَّث)، لكن كل طلبات السكربت واللعبة التالية (المباني، الإرساليات، الترقيات) تُنفَّذ على القلعة الجديدة. اللوحة تعرض دائماً القلعة النشطة الحقيقية في الشارة أعلى النافذة.

### تبويب الأمير (مهام المدينة)
- يدمج وظيفة سكربت **Prov2026** القديم: إرسال الأمير لمهمة المدينة المتاحة، لكن عبر **Ajax فقط وبدون أي تنقّل**:
  - `GET province.php` → يقرأ الفتحات الأربع وأي فتحة فيها مهمة متاحة (`slotAction(2, <id>)`).
  - `POST province.php` → `action=2&id=<id>` → نافذة المهمة (نتأكد من وجود `#attendBtn`).
  - `POST province.php` → `action=3&id=<id>` → إرسال الأمير (رد النجاح: `{"data":{"error":false}}`).
- يعرض جدولاً بالفتحات: **متاحة** / **الأمير في مهمة** (مع العدّاد المتبقي) / **بانتظار المهمة**.
  - بعد الإرسال تبقى الفتحة ظاهرة في اللعبة مع مؤقّت `Timers.add(…, <ثوانٍ>, 'slot_timer_<N>')`؛ السكربت يقرأ هذا المؤقّت ويمنع إرسالاً مكرراً حتى انتهائه.
- **⚔ إرسال الأمير الآن** — يعمل من **أي صفحة**، ويختار أول مهمة متاحة لم تُرسَل.
- **مفعّل لهذه القلعة** — يُحفظ في `localStorage['prov']` بنفس صيغة السكربت القديم:
  `{"اسم القلعة": true|false}` — غياب المفتاح = مفعّل. (لذلك إعداداتك القديمة تبقى محفوظة.)
- **تلقائي من أي صفحة** — لا يتطلب فتح `province.php` ولا أي تأكيد: عند تحميل أي صفحة يحاول بعد أقل من ثانية، ثم يعيد الفحص كل 30 ثانية. يختار أول مهمة متاحة ويرسلها مباشرة (تبويب الإعداد `kw.provinceAuto`، افتراضي مفعّل، مع تهدئة 30ث بين التبويبات). عند إيقاف الخيار أو تعطيل القلعة يتوقف فوراً.
- سجل قصير يعرض آخر المحاولات وأخطاء السيرفر كما هي.
- لا يقرأ قوات الأمير ولا يغيّر أي شيء آخر. عند رفض السيرفر (شرط غير مكتمل مثلاً) تظهر رسالته ويبقى كل شيء كما هو.

## كيف يعمل (باختصار)

- `@grant none` → يعمل داخل سياق الصفحة، فيستخدم `window.Ajax.Request` الخاص باللعبة.
- على `marches.php`: يستدعي `marches.loadContent()` الحقيقية ثم يقرأ الـDOM الحيّ.
- على أي صفحة أخرى: يرسل نفس طلب `POST ajax_marches.php` مع `type=loadContent`، **بدون أي تنقّل**.
- الوقت المتبقي من `data.timers`، والمدة الكلية من `data.marchTimes`.
- التقدّم يُحسب بمعادلة اللعبة: `100 * (1 - timeLeft / timeTotal)`.
- السكان والحمولة ووقت الوصول/العودة من `info.php` (`what=pohod`).
- القلاع من `ajax_castles.php` (class `current` = القلعة النشطة).
- التبديل عبر `main.php?tpid=` باستخدام **`fetch` وليس `Ajax.Request`**: رد `main.php` نوعه `text/javascript` ويحتوي `window.location = ...`، ونسخة Prototype في اللعبة تنفّذ ردود الجافاسكربت تلقائياً، فأي تبديل عبر `Ajax.Request` يُنقل الصفحة فعلياً. `fetch` لا ينفّذ شيئاً.
- البناء الآلي يستخدم **نفس** طلب الترقية الذي تستخدمه الواجهة (`buildings.php?tb_id=N&method=ajax`) ويصنّف رد الخادم (`error:0` / `error_txt`) بدل تخمين النتيجة من الصفحة.
- **التحقق من نجاح الترقية** لا يعتمد على الردّ وحده: يقرأ المستوى قبل الإرسال (`ajax_buildings.php`)، ثم يقرأه فوراً بعد القبول (لأن اللعبة قد تُظهر المستوى التالي مباشرة)، وإن لم يظهر ينتظر فراغ جدول البناء ويعيد القراءة. لا يُحذف العنصر إلا إذا ارتفع المستوى فعلاً. الترقية المعلّقة تُحفظ في `kw.pendingBuilds` حتى لا تُفقد عند إعادة التحميل.
- **مكافآت المهام** تُستلم عبر نفس مسار اللعبة (`ajax_quester_v63.php`، `Quest_UI_Base` + `claimReward`)، وفقط عند `isClaimable = true`.
- **لا يقرأ** وحدات القلعة (`armyPresent`/`armyCapacity`) ولا الوحدات داخل الإرسالية (`units`).

## حدود وأمان

- لا حقن موارد ولا استغلال ثغرات — القراءة والترقية فقط عبر نفس طلبات الواجهة.
- استلام المكافآت يقتصر على المهام التي تعلن اللعبة أنها `isClaimable`؛ لا نفرض استلام مهمة غير مكتملة.
- يمكن أن يحتوي جدول البناء على **عنصرين** كحد أقصى؛ لا يرسل السكربت أكثر من الحد الذي يعلنه الجدول الحقيقي.
- الدوران بين القلاع مخصّص للحسابات التي تملك **أكثر من قلعة**؛ مع قلعة واحدة تُعطَّل الأزرار تلقائياً.
- البناء الآلي يصرف موارد حقيقية ويأخذ طابور البناء — لا تشغّله إلا وأنت تريد الترقيات فعلاً.
- كل صفحة جديدة تُحمّل السكربت من جديد تلقائياً (لا حاجة لإعادة لصق).
- ضبط «التحديث التلقائي» يزيد عدد الطلبات؛ اتركه مغلقاً أو على 30–60ث.
- اللوحة تُحفظ حالتها (الفتح/التبويب/الموضع/الفاصل) في `localStorage` بنفس نطاق اللعبة.
